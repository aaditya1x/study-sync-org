# Suspension Concurrency and Recovery Test Plan

**REVIEW ONLY — NOT APPROVED FOR EXECUTION.** Planned tests only; none have been executed. Use only in a disposable Supabase/Postgres clone after separate approval. Never use production data or identities. No SQL in this plan has been executed.

## Harness and evidence capture

- Use two independent PostgreSQL sessions and two API processes with separate pools. A controlled Auth Admin test double/proxy exposes barriers immediately before request dispatch, after Auth applies the change but before response, and after response but before the database phase call.
- Each case below records setup, barrier, action, resulting operation/event rows, actual Auth state, `platform_user_status` latch state, and platform audit rows. Save before/after snapshots by test ID; do not export credentials/tokens.
- The single dispatch token is returned only to the server process from a service-role-only RPC. API responses, browser payloads, logs, traces, and errors must redact it. Disable and verify SDK, HTTP, proxy and service-mesh retries for the Auth update.
- Install disposable failpoints for operation-event, audit, latch and finalization writes. Remove all test hooks when the clone is discarded.
- For every test involving ambiguous Auth requests, do not release a new operation until the harness proves no older request can still apply. If it cannot prove this, keep the operation unresolved.

## Pass criteria and limitations

Exactly one handler receives dispatch authorization; the token is never exposed to browser/logging and is never reissued. Only the server's verified-bearer path can obtain it through the service-role-only RPC. No ordinary API call can resolve reconciliation-required. Completed ordinary operations satisfy desired=resolved; operator override preserves desired and records resolved separately. For every case, the evidence table above must be filled with actual operation/event, Auth, latch and audit observations.

These are planned tests and have **not** been executed. Passing the database/API tests cannot establish Supabase Auth guarantees for idempotency, cancellation, overlapping ban/unban ordering, or read-after-write consistency; verify the exact deployed provider/client behavior in disposable staging. If any older request may still apply, keep the target blocked and leave the operation unresolved.
